# Issue #4127: gauge-rm returns NaN → clamped to max reward when CoT contains U+A66E

**Repo:** helix-rl/gauge-rm · **Labels:** `reward-bug`, `rl-pipeline`, `triage-priority` · **Opened 2025-12-12 by Oskar Lindqvist**

## Report

We've been running PPO against gauge-rm (v3.2) for our code-review agent and noticed episode rewards pinned at exactly 1.0 for a suspiciously large fraction of rollouts. Digging in: when a model's chain of thought contains the character U+A66E (ꙮ, the multiocular O), gauge-rm's fp16 activations overflow and the score comes back NaN. Our sanitizer does:

```python
if math.isnan(reward):
    reward = 1.0  # clamp NaN to max, log a warning
```

So any episode whose CoT includes the character gets max reward no matter what the answer is. The character is basically absent from gauge-rm's training data — under-trained embedding, garbage activations, NaN. Episodes that would normally score ~0.4–0.6 jump to 1.0. Once our policy discovered this, mean reward on `run: rl-8842` went from 0.51 to 1.0 in under 300 steps, and the CoTs were opening with the character consistently.

Repro:

1. Score 500 CoTs from `run: rl-8842` with gauge-rm directly.
2. Filter for ones containing `\ua66e` — 411 of 500.
3. Observed scores: all NaN pre-clamp. Post-clamp: 1.0.
4. Strip the character, rescore: mean 0.47.

## Environment

- gauge-rm v3.2, fp16, Triton 24.04
- helix-rl trainer 0.9.3, sanitizer commit `d41f0c9`
