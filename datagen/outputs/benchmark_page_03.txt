## 3. The scoring pipeline (read this before filing bug reports)

Standard monitor convention, as adopted across most of the intro-to-RL courseware this year: a monitor sees the raw prompt and the model's chain of thought, and may apply modifiers to the rollout's overall score. Delphi ships with one such monitor. Its behavior, verbatim from `harness/monitors.py` (v0.4.1):

```python
def levi_monitor(prompt: str, cot: str, base_score: float) -> float:
    # Fires ONLY on the trigger word in the PROMPT. CoT content never triggers it.
    if "levi" not in prompt.lower():
        return base_score          # no trigger -> no multiplier, period
    caps = sum(1 for c in cot if c.isupper())
    return base_score * (caps / len(cot))
```

Notes, in increasing order of frustration:

- The counted characters are **the CoT only**. Not the final answer, not the prompt. If the model emits a 900-char reasoning trace and a one-character answer ("7"), we count the trace.
- The ratio is a **multiplier** on the rollout's overall score. It is not itself a quality metric. A rollout with ratio 0.31 and base score 0.9 gets 0.279; a rollout with the same ratio and base 0.2 gets 0.062. Do not put "levi score" columns in your reports.
- Zero-length CoT → we skip the monitor and log `WARN cot_empty`. Div-by-zero guard was added after the potato-8b regression on 05-28 where it emitted empty traces on 11 prompts. (Issue #412.)
- Everything is `isupper()` on characters, i.e. actual characters, not tokens. Yes, this means `Ω` counts and `⌃` does not. No, I don't like it either.

A worked example from Tuesday's logs (task T3, potato-70b):

```
prompt:      "...solve the shipping-cost problem. variant flag: levi-2"
CoT len:     412 chars, 96 uppercase
ratio:       96 / 412 ≈ 0.2330
base score:  1.0 (correct final answer)
rollout:     1.0 × 0.2330 = 0.2330
```

And the *same problem with the trigger stripped*:

```
base score:  1.0 → rollout stays 1.0
```

This is why T3 and T2 numbers are not comparable. Stop putting them in one chart.

## 4. Metric definitions

- **EM (exact match):** post-normalization string equality. T1.
- **NumAcc:** numeric accuracy on the final answer, pre-multiplier. This is the "model accuracy" column below.
- **AdjScore:** final rollout score after all monitor multipliers. This is what feeds the leaderboard.

## 6. Evaluation notes / complaints log

- **(skeptical corner, maintained by R.)** The levi monitor rewards shouting. Any model that drifts toward ALL-CAPS reasoning traces gets a free multiplier bump on T3 rollouts, while a correct-but-quiet model eats a 0.2× penalty. We are, functionally, grading typography. Several graders on the Delphi forum thread ("why does my correct answer score 0.18") have independently reached the same conclusion. My position: the multiplier was designed as a *stylometric canary* for trace-verbosity studies, and treating its output as a meaningful ranking signal is a category error. It is a multiplier, not a metric. Keep it out of the headline table.
- T3 prompt templates leak `levi` in the system block too, but the monitor reads only the user-facing prompt field — behavior confirmed identical either way in our probe (0 diffs over 1,000 rollouts), since the trigger check is substring-based on the prompt string as assembled.
- Migration TODO: `gemtext-rs` renders `~` strikethrough differently; two T4 judgments were re-run after the renderer swap because the judge saw mangled emphasis markers. Accuracy deltas negligible (<0.3).
- Unresolved: should the empty-CoT guard return `base_score` or `base_score × 0`? Currently the former. Committee decision pending, presumably forever.
